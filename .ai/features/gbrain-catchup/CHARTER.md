# Build Charter: Catch the fork up to upstream gbrain

**Slug:** gbrain-catchup  ·  **Date:** 2026-10-05  ·  **Repo:** absi-brain (fork of garrytan/gbrain)
**Entry point:** plan   ·   **Framing:** EXTEND (pure upstream catch-up, no fork features)
**Surface:** two live `gbrain serve --http` brains (personal :3131, family :3132) used by a chat bot over MCP
**User-facing:** no UI; the user meets it through the bot's memory

## 1. Problem & demand
- User: the owner, via a personal chat bot whose long-term memory is these two brains.
- Status quo: the fork runs v0.42.53 (2026-06-23); upstream is v0.60.48 (~1,460 commits, schema 119 → 199).
- Pain: missing many fixes for silent failures, privacy leaks, Windows breakage and PGLite speed; one
  uncommitted local patch (Ollama chat recipe) keeps local synthesis working and blocks clean pulls.

## 2. Core user journey (gate 1)
1. The bot saves a memory to the personal brain → the save is acknowledged.
2. The bot searches for it → the new page comes back, alongside pages that existed before the upgrade.
3. The bot asks the brain to think over it → a synthesized answer, generated by the local Ollama model (no paid call).
4. The same save / search on the family brain → works, and the two brains stay separate.
5. **Goal:** both brains run the latest upstream with every pre-upgrade page intact; the bot needs no changes.

## 3. Verification contract (gate 2)
Primary approach: API journey (the bot's own MCP path with its real token) + one real bot conversation in a test thread.
- **M1 Safety net** — 1) WHEN backups are taken SHALL each brain have a copy whose page count matches live.
  2) WHEN a backup copy is opened by the old version on a spare port SHALL it serve search. 3) IF a copy is
  incomplete THEN the run SHALL stop before touching anything live.
- **M2 Code + toolchain** — 1) The branch SHALL equal upstream master plus `.ai/` only (no stray fork diff).
  2) The Ollama patch SHALL be gone, kept only on its backup branch. 3) Typecheck + upstream unit suite SHALL
  pass on Windows with Bun ≥ 1.4 (pre-existing upstream failures recorded, not new ones).
- **M3 Rehearsal on copies** — 1) WHEN the new version opens a copy of each brain SHALL every migration apply
  and `doctor` report no errors. 2) Page, chunk, tag and timeline counts SHALL match before/after.
  3) Five known pages per brain SHALL be found by search. 4) `think` SHALL answer via the local model.
  5) Bot-side round-trip (save → search → think) SHALL pass against the rehearsal server. 6) IF a migration
  fails THEN the live brains SHALL be untouched.
- **M4 Cutover** — 1) Fresh backup immediately before. 2) Both pm2 apps restart on the new code and answer
  `/health`. 3) The M3 journey passes against the live ports. 4) IF any check fails THEN restore backup + old
  code + old Bun automatically and report.
- **M5 Settings** — 1) `auto_chronicle` set explicitly per the owner's choice. 2) Restart notices cleared;
  `doctor` clean. 3) Chosen follow-ups added to the roadmap.
Independent verifier (did not do the upgrade) re-runs M3–M5 checks on the live brains + one real bot
conversation; evidence = transcripts + doctor output.

## 4. Scope
- Scope mode: hold. In: code catch-up, Bun upgrade, migrations, both brains, the auto_chronicle setting.
- Out (follow-ups, own runs): Gmail open-loop engine, ChatGPT/Claude history connectors, Tailscale exposure,
  repo onboarding (`.ai/` memory) — done right after, on the new code.

## 5. Behavior & edge cases
- PGLite is single-writer: rehearsal uses copies on spare ports, never the live files.
- Bun is global: rehearsal uses a side-by-side Bun ≥ 1.4 binary; the global Bun changes only at cutover.
- Brain config (incl. the local model routing) lives in the DB and carries over with it.

## 6. Architecture decisions
- Fast-forward to upstream rather than cherry-pick: the fork has no commits of its own.
- Drop the Ollama patch: upstream ships Ollama chat (custom tags accepted, reasoning headroom handled).

## 7. Autonomy boundary
- Default breakers ON. Custom: never delete a backup; never touch the live DB files except at cutover.
- Merge policy + cutover authorization: per the owner's answer (see LEDGER).

## 8. Definition of done & deliverable
- Six spine gates green. Delivery Pack uploaded to the owner's chat.
